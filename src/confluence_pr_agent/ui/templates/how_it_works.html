Full flow diagram (every branch, including the optional approval gate)
{% include "_flow_diagram.svg" %}
1 · Confluence page changes

A Confluence spec page is edited and saved. Confluence sends a webhook (or, for a demo, Simulate Webhook triggers the same code path manually). The agent fetches the page's current content and diffs it against the last version it successfully processed -- computed as a unified diff of the page's plain-text content, not raw HTML, so formatting-only edits don't trigger a false change.

If Confluence label filtering is configured, a page without at least one allowed label is ignored here before any repo work happens. If the version bumped but the content is unchanged (e.g. a metadata-only edit), the run also stops here.

2 · Jira story filed (optional)

{% if settings.jira_enabled %} Before any code is touched, a Jira story is created from the spec diff alone -- summary, description, and acceptance criteria written by an LLM. No separate key needed: it uses the LLM Judge's own provider/model below if that's configured, otherwise falls back to the Gemini key from the Change Engine tab (or a plain, non-AI-authored summary if neither is available), then filed in {{ settings.jira_project_key }} as a {{ settings.jira_issue_type }}. If the spec changes again while that story is still open, the pipeline comments on it instead of filing a duplicate -- one story per page, same idea as the PR-reuse behavior below. {% else %} Currently disabled (JIRA_ENABLED=false in Configuration) -- the pipeline skips straight to cloning the repo. Turning it on tracks every spec change as a Jira story automatically, with no other change to the rest of this flow. {% endif %}

Best-effort, like the email step at the end: a Jira outage or missing config never blocks the rest of the run. Once the run finishes, the story gets one more comment -- either the resulting PR link, or an explanation of what went wrong, so a developer can pick up a failed run manually.

3 · Clone the target repo

The pipeline clones {{ settings.target_repo }} at its base branch ({{ settings.target_repo_base_branch }}) into a fresh working directory and creates a new branch for this change -- one clone per run, so nothing from a previous or concurrent run leaks in.

4 · An AI agent implements the change

A pluggable coding agent reads the repo, understands its conventions, and implements the spec change directly -- writing or updating tests as part of the same change, not as an afterthought. This run is currently configured to use {{ settings.change_agent_engine }}, but the choice (Claude Code, Cursor, GitHub Copilot, Codex, Gemini, Antigravity) is a config switch, not a code change -- see Configuration.

If the agent fails outright, or makes no file changes at all, the run stops here with nothing pushed anywhere -- this is the one failure mode nothing downstream can recover from.

5 · Gate -- the repo's own tests (with self-correction)

The target repo's own test command ({{ settings.target_repo_test_command }}) runs against the change, unmodified. This is a mechanical check: does the code still work, by the repo's own definition of "works"? On a failure, the agent gets another attempt with the failure output fed straight back into its prompt -- up to {{ settings.change_agent_max_attempts }} attempt{{ "s" if settings.change_agent_max_attempts != 1 else "" }} total -- before giving up. Only if every attempt still fails does the run end as Tests Failed, with the Confluence page version deliberately not marked as processed, so the exact same diff is retried on the next webhook rather than silently dropped. This is the only other failure mode that blocks a PR.

6 · LLM Judge review (advisory, not a gate)

Passing tests doesn't prove the spec was actually implemented -- a green suite can't tell the difference between "correct" and "coincidentally didn't break anything." This is a semantic check: an independent model ({% if settings.judge_enabled %}currently {{ settings.judge_provider }}{% else %}currently disabled{% endif %}) scores three criteria independently -- does the diff implement the spec, is it scoped to just that change, do its tests actually cover the new behavior -- each as pass, warning, or fail.

Unlike the tests gate, this never blocks the PR from opening -- there's no one present mid-run to act on an internal "are you sure?", so it only changes what kind of PR opens next. Any "fail" opens a PR anyway, titled [Needs Work] and marked as a draft, with the full rubric and the judge's reasoning written directly into the PR description. A "warning" with no "fail" still opens a normal PR, just flagged ⚠️ warning on the run so it's easy to spot for a closer look. If the judge's own API call isn't configured or fails, this step fails open (skips the review) rather than blocking a change that otherwise passed its own tests.

Independent of the change engine on purpose, in both provider and model, so it isn't the same model grading its own work. Toggle it, and switch between Anthropic and OpenAI, from Configuration.

7 · Pull request opens (or updates in place)

Once tests pass, the change is committed and pushed, and a PR opens against {{ settings.target_repo_base_branch }} -- with the agent's summary, the LLM judge's rubric (when one ran), and the list of changed files in the description, plus a link back to the source Confluence page. This always happens once tests pass, regardless of the judge's verdict -- only the title and draft/normal state change. Only now does the pipeline record this page version as processed.

If the spec changes again before the last PR for this page is merged, the pipeline checks whether that PR is still open. If it is, the new increment is pushed onto its existing branch and the PR is updated in place (title, body, labels) instead of opening a second PR -- one review thread per page, not one per edit. Any commits a reviewer already pushed to that branch are fetched first and built on top of, never overwritten; if that update can't be completed cleanly, the run reports an error rather than risking either a lost review comment or a silently duplicated PR.

A rejected or warned PR also carries a agent:needs-work or agent:warning label (in addition to the title/draft state), so either state is queryable via the GitHub API or CLI, not just by matching PR titles.

8 · Team notified

A summary email goes out to the configured recipients with the spec diff, the change summary, and a link to the PR. This step is best-effort and deliberately isolated from everything before it -- an unconfigured or failing email step never turns an already-opened PR into a reported failure; it just shows up as "not sent" on the run.

If a Jira story is being tracked (step 2), it gets commented with this same PR link at the same point -- or, on a run that ended in an error or still-failing tests instead of a PR, with an explanation of what went wrong so a developer can pick it up by hand.
